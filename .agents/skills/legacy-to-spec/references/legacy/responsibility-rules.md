# 耦合責任拆解

**職責**：把混合邏輯分配到前端、後端及 HANDOFF。來源還原依 [JSP 解析](./jsp-analysis.md)，權威核對依 [authority](../api/authority.md)。

## 先還原，再分責任

- **還原內容**：觸發、資料、判斷、條件、順序、時間關係及副作用。
- **分類依據**：執行位置不等於責任；不能用 JSP／JavaScript／檔名直接判定。
- **LOGIC 索引**：history/evidence 記 E-ID、FLOW、DATA、判斷、執行位置、責任方、UI／API／HANDOFF 去向、版本及 TODO。

| 責任方 | 內容 | 契約去向 |
| --- | --- | --- |
| **前端** | 資訊呈現、操作順序、焦點、可見狀態、回饋與互動 | UI spec |
| **後端** | 受信任身分／權限、業務裁決、可信狀態、持久化、交易及跨系統副作用 | 已確認 API 契約或 HANDOFF |
| **未確認映射** | 已知需求但承接能力／版本不明 | 局部 TODO 與具體查證任務 |

- **前端檢核不是業務保證**：可保留操作限制，不把 client 或原型裁決當後端保證。
- **拆解不是改良授權**：保留中間狀態、觸發與原有體驗，不自行改 UX。
- **需求不是服務存在證據**：混合來源可證明舊需求，目標後端需另有承接依據。

## HANDOFF 必填內容

HANDOFF 保留在 [API spec](../../templates/spec/api-spec.md)，不另建移交文件。

| 欄位 | 內容 |
| --- | --- |
| **需求與責任** | 已知需求、legacy E-ID、原責任及擬承接方 |
| **觸發與情境** | 事件、前置狀態、可信 context 與權限需求 |
| **輸入／輸出** | 資料語意、條件、合法來源與未知內容 |
| **處理保證** | 順序、交易、失敗、取消、時間及副作用；只記已證實範圍 |
| **關聯契約** | FLOW／BOUND／DATA／ST／BR／MSG、US／UC 及 AC |
| **承接依據** | 產物、版本、存在／承諾／未確認／未提供的差別及 TODO |

**HANDOFF 是需求與責任界線**，不是後端已實作證據；不能捏造 method、path、response 或原子性。

## 後續映射

- **契約保留**：第一版先記已知責任，後續適用 PRD／UI/API／BDD 沿同一 ID 引用。
- **缺口回補**：取得承接依據後依 [dependencies](../../guides/dependencies.md#取得證據後回補) 更新規格與必要驗證。
- **原型展示**：遵守 [UI 原型邊界](../ui/writing-rules.md#資料服務與展示替身)，不以未知承接結果展示成功。
