# 前後端權威分工

## 權威不是全域排名

每項主張先辨識責任，再選適用來源。指定 `backend_root` 與本輪後端產物路徑、版本／雜湊和適用環境；前端根入口也需獨立鎖定版本。不同發布版本、legacy 語意規格、設計稿與 stub 不得拼成一份現行契約。

| 主張 | 權威 | 另一端的用途 |
| --- | --- | --- |
| 畫面、資訊層級、操作順序、UI 狀態、共用元件與使用者導覽 | 前端 JSP、script、style、include、元件與執行觀察 | 後端可說明資料及結果，不決定 UI 版面或互動 |
| API operation、method、path、wire 欄位、型別、格式、必填、回應 envelope、結果碼 | 指定版本的 eBAF 後端轉換產物 | 前端提供消費需求，不新增或改名後端欄位 |
| 業務運算、資料存取、交易、副作用、服務端授權與受信任情境 | 後端業務規格、已確認設計與適用實作契約 | JSP 可證明 legacy 行為或揭露後端遺漏，但不能據此宣告目標 API 已支援 |
| API 欄位與前端 DATA／UI、結果碼與 TR／ST／MSG 的映射 | 各端在其責任內的證據共同成立 | 任一端缺證據即列缺口；不以名稱相似當映射依據 |
| JSP 內尚未被後端產物承接的後端邏輯 | JSP 作為舊行為證據；目標後端需承接紀錄 | 形成 `HANDOFF-*`，不直接升格為 API 契約 |

前端「欄位必填」與 API「欄位必填」分開記錄。前端可保留已證實的操作限制，但不能修改後端接受條件；後端要求的傳入資料在前端無合法來源時列介接缺口，不任造預設值。

訊息的語意與顯示位置由前端負責，後端回傳文字、代碼及動態值由後端負責。若前端已存在固定映射，引用其證據；若直接顯示後端訊息，保留後端原文。兩端差異必須明列，不能以文案整理掩蓋相容性問題。

## 選定後端基準

1. 優先使用使用者或後端交付紀錄指定的發布契約；若分析的是規劃版本，標示「設計契約」，不宣稱已部署。
2. 搜尋 [後端設計參考](backend-profile.md) 所列產物類型，確認檔案存在、版本、用途與適用範圍。`.github` 的指導文件與範本是方法參考，不是本頁 API 的正式證據。
3. 若只取得 `docs/specs` 方法規格，可確認業務語意，不自行推導 HTTP path、序列化名稱或 envelope。若只取得 controller 設計而缺少共通回應定義，保留後者的未知。
4. 同版本文件與實作或觀察不符時，兩者都登錄 E 並建立 TODO；除非有明確的基準選定／變更紀錄，不以修改時間或「程式一定較新」自行取捨。
5. 若已有明確的基準選定紀錄，選定產物可用於目標 API；與前端原行為的差距仍需留痕，不代表前端可任意改變可見契約。

未取得後端基準只阻塞對應的 API／業務主張；其餘前端分析可繼續。部分 API 已證實時可以交付該部分，未知操作不得填入假 path、空 schema 或成功範例。

來源性質與可用環境也要忠於原文：設計／展示文件不能證明已部署，也不能證明未部署。後端沒交付呼叫環境時記錄環境缺口，部署狀態另列未確認；不把測試的存取限制當成系統事實。

## 共用元件

以前端共用來源本身及其呼叫位置建立 `CMP-*`，記錄來源版本、已知輸入、顯示、事件、狀態與各使用處差異。後端代碼清單或回應結構不是 UI 元件權威。

本輪只分析支撐根 JSP 的元件用法，不因一個 include 就宣稱已涵蓋所有頁面。重用既有元件規格時以 `<scope-id>/CMP-*` 連到原規格及版本；若發現差異，補證據或 TODO，不另建同名但語意衝突的「標準元件」。

## 增量同步

後端基準更新時，逐項核對操作、欄位、結果碼、格式與語意，更新 API 消費投影和受影響的 FLOW／DATA／TR／AC。前端元件變更亦需反查使用處；記錄於 tracking，不改寫外部後端檔案。
