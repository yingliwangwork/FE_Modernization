# 規格翻新驗收

## 交付判定

範本刻意含 `{{...}}` 佔位符；實際交付不得留下佔位符、空表格示例列或未替換的骨架。必要章節沒有事實時，保留具體未知及 TODO 指向，或有依據的不適用說明，不強求每章產生內容。

| 檢查 | 通過條件 |
| --- | --- |
| 單一入口 | tracking 恰有一個根 JSP，來源版本可辨識，依賴不冒充第二個入口 |
| 範圍 | 納入、排除、交接及未取得依賴有明確邊界；部分分析不得聲稱完整入口 |
| 技術中立 | 前端系統規格不依賴框架、程式符號、端點或儲存實作；API 精確傳輸契約獨立保留，使用者可觀察的格式、文案與代碼不丟失 |
| 事實性 | 每項行為與意圖可定位 E；未知和衝突有 TODO；沒有以慣例填入需求 |
| 完整性 | 每個已辨識事件、條件分支、UI、資料交換及副作用在覆蓋表有去向；未辨識依賴仍列為缺口 |
| 流程可實作 | 每個 FLOW 能判定觸發、前置條件、判斷順序、反應、可見結果及後置狀態；未知部分分開標記 |
| 狀態一致性 | TR 的起始／終止 ST、條件、UI 與訊息引用有效；已知分支均可對照流程與案例 |
| 視覺一致性 | SCR／ST／UI 和 prototype 可雙向核對，交互操作符合 FLOW；沒有多出的產品功能 |
| 驗收可驗證 | AC 定義前置資料、事件、具體預期；V 記錄實際操作及結果，不以程式碼推論取代執行 |
| 分離與維護 | 排程、進度、TODO 細節、來源語法、驗證執行與增量歷史只在 tracking；連結及 ID 可解析 |
| 權威分工 | 前端定義 UI／UX／CMP，指定後端產物定義 API／業務能力；版本和發布／設計／stub 性質可辨識；沒有使用 .github 範本冒充操作契約 |
| API 轉寫 | 每個已取得 API 的操作、輸入、共通 envelope、輸出、錯誤與必要引用和後端基準相符；未知內容未被自創欄位／端點填補 |
| 雙向映射 | FLOW／BOUND→API→DATA／TR／ST／MSG 可核對，所有必要輸入有合法來源，轉換規則有兩端證據，未消費輸出有範圍理由 |
| 耦合拆責任 | 每項已盤點 LOGIC 有分類及去向；後端責任有承接證據或 HANDOFF／TODO，原順序、受信任情境與已知交易要求未丟失 |
| 共用元件 | CMP 的定義與本頁用法以前端為依據；相關的條件式反應逐分支保留，選用情境未知不掩蓋已知行為；跨 scope 重用可定位版本，不從單頁推廣成全系統標準 |

## 覆蓋與結果

來源覆蓋表要包含可見區塊和條件渲染，以及非可見的初始化、hidden 狀態、外部回應和副作用。每列必須是已映射、有具體 TODO，或有證據的排除；不能省略未知列來提高完成率。

驗證案例涵蓋已知的主路徑、所有可辨識條件分支及有證據的失敗／取消／空值情況。沒有證據的分支不要編成需求。若報告覆蓋率，分母是已盤點項目並明列盤點限制，不能宣稱未知依賴已覆蓋。

完整交付需範圍內必要契約均已確認、無未解矛盾、來源覆蓋無缺口，並完成必要的文字、視覺及互動驗證。執行環境或資料不足時保留部分交付與限制。時間、篇幅、檔案數與 TODO 數歸零皆不足以單獨證明完整。

有 API 或後端移交時，還要核對後端基準與投影是否一致、JSP 後端責任是否有承接依據。只有文件、設計稿或 stub 驗證時，分別標示契約核對結果與介接驗證限制；不能宣稱已與正式後端介接。來源版本變更後，相關映射與驗證須重新判定，舊的通過紀錄不自動沿用。

若已有設計確認要求，沿用其權限與流程；本規則不新增一律需人工批准的關卡。交付不包含部署、發布或重寫原始碼。
