# Legacy to Spec：翻新框架與流程

## Goals

1. **Primary**：產出可理解、可追溯、可驗證的技術中立系統契約與視覺成果，保留已有證據的意圖和體驗。
2. **Secondary — 依賴與增量**：先建立翻新計劃，再辨識外部資源、依賴與影響；重用適用契約，依使用者決策逐步補齊缺口。
3. **Secondary — 分離與維護**：分離系統設計、跨邊界契約與翻新執行紀錄，讓每次小範圍交付可持續維護。

## Constraints

- **Scope**：每輪只有**一個入口來源**；依賴分析不自動授權擴大翻新範圍。
- **Evidence**：**不以推測補造**行為、意圖或外部能力；未建立、未知與衝突保留可定位的缺口。
- **Preservation**：還原已有契約；變更行為需有可定位的確認依據。

## Rules

翻新的成果是**可理解、可追溯、可驗證的系統契約**。以系統在特定情境下接收什麼事件、做出什麼反應，以及使用者能觀察到什麼結果，取代對既有實作語法的重述。

### R1: 證據先於描述

- **REQUIRED**：行為與意圖主張需有**直接來源、可重現觀察或可定位的確認紀錄**。未知或衝突保留具體缺口、各方證據與影響。
- **FORBIDDEN**：以命名、慣例或經驗代替證據，或自行裁決衝突。分類與轉譯依 [證據規則](guides/evidence.md)。

### R2: 保留意圖與體驗

- **REQUIRED**：保留**資訊層級、操作順序、狀態、回饋、限制、副作用與跨邊界互動**，包含事件的作用範圍、時間關係與生命週期。
- **Change Control**：原有缺陷與改良提案分開記錄；不得為展示方便改變觸發、取消時機或中間狀態。

### R3: 權威依責任分配

- **Authority**：畫面、互動與共用呈現以**前端來源**為權威；服務能力、交換契約與業務處理以**後端產物**為權威。
- **REQUIRED**：跨邊界映射需**兩端依據**；鎖定適用版本，分清既有事實、設計承諾與展示替身。依 [權威分工](references/api/authority.md) 揭露差距，不補造能力。

### R4: 耦合必須拆責任

- **REQUIRED**：還原事件、資料、判斷、順序與副作用後逐項分責任；**執行位置不等於責任歸屬**。
- **Responsibility**：呈現屬前端，業務決策與受信任狀態屬後端；未承接部分依 [責任拆解](references/legacy/responsibility-rules.md) 建立移交需求。

### R5: 以觸發與結果組織契約

- **REQUIRED**：每個流程說明**觸發者、事件、前置狀態、條件、系統反應、可見結果及後置狀態**。使用者、系統生命週期與外部回應皆可能觸發流程。
- **Neutral Description**：以行為與資料語意描述契約；來源符號及實作步驟留在追蹤映射。
- **Branch Preservation**：保留已知的條件式分支。情境是否成立未知，不抹除已知分支反應；未知結果不偽裝成成功。

### R6: 先計劃，再沿依賴推進

- **Plan First**：分析前建立入口、初始邊界與任務計劃；每項任務有**依賴、影響與驗證條件**。
- **Reuse and Decision**：依 [依賴與決策](guides/dependencies.md) 引用適用契約。未轉換資源告知使用者，由其決定先翻新或延後；沿用明確授權，**沉默不是決策**。
- **Deferred Gap**：延後時在每個受影響契約位置標記 **TODO**，連到追蹤詳情與後續任務。

### R7: 小範圍累積

- **Traceability**：沿用**穩定識別碼**補充契約和缺口。版本變動回查受影響範圍，保留被取代的證據與決策；續作依 [工作流程](guides/workflow.md#驗證與續作)。

### R8: 契約與執行分離

- **Separation**：設計規格描述**系統應有的可觀察行為**；翻新追蹤描述**分析、待辦、驗證與進度**。兩者透過識別碼互相連結，不把工作排程寫成系統需求。
- **Style Consistency**：有樣式設計的元件**同時交付樣式規格與視覺成果實際使用的樣式**，逐項核對；客製化不改變證據或權威要求。
- **Consistency**：視覺原型與文字契約共用**同一套行為事實**；展示用資料與審閱工具不能變成新需求。

### R9: 完整性必須能被檢查

- **Evaluation Basis**：依 [驗收規則](guides/acceptance.md) 核對已界定範圍的來源、契約及驗證覆蓋。沒有發現不等於不存在，未取得不等於不適用。
- **Partial Delivery**：必要契約或驗證仍缺少時，標示**部分交付及限制**。

## Examples

### E1: 已知觸發，未知結果

- **已知條件**：來源證明一個事件會引發外部交接，但未取得交接後的結果。
- **CORRECT**：描述已知觸發與傳遞資訊；將未知結果及影響連到缺口與後續查證。
- **INCORRECT**：把未取得的結果描述成成功，或因結果未知而省略已知觸發。
- **對應規則**：[R1](#r1-證據先於描述)、[R5](#r5-以觸發與結果組織契約)、[R9](#r9-完整性必須能被檢查)。

### E2: 適用契約與未轉換依賴

- **已知條件**：一項依賴有適用契約，另一項尚未轉換，且使用者尚未決定如何處理。
- **CORRECT**：引用已核對的契約；記錄另一項依賴的缺口與影響，告知使用者並維持待決，只繼續不依賴該決策的工作。
- **INCORRECT**：重複翻新適用契約，或把未回覆視為同意擴大範圍或延後。
- **對應規則**：[R6](#r6-先計劃再沿依賴推進)、[R7](#r7-小範圍累積)。

### E3: 需求存在，承接未確認

- **已知條件**：呈現所需能力有來源證據，但負責處理該能力的一方尚未提供承接依據。
- **CORRECT**：保留已知呈現需求、責任界線與具體移交缺口；展示停在已知邊界。
- **INCORRECT**：由呈現需求推導處理能力已存在，或把展示替身視為已承接的證據。
- **對應規則**：[R3](#r3-權威依責任分配)、[R4](#r4-耦合必須拆責任)、[R8](#r8-契約與執行分離)。

## Workflow

1. **建立計劃**：依 [工作流程](guides/workflow.md) 鎖定唯一入口與版本；依 [範本客製化](guides/customization.md) 選用交付範本。
2. **盤點依賴**：查找適用契約並記錄依賴、影響與決策。未決部分保持待決，只繼續獨立工作。
3. **形成行為契約**：依證據盤點資料、狀態、事件與分支；需要解析來源時讀 [來源解析](references/legacy/jsp-analysis.md)，混合責任依 R4 拆解。
4. **形成邊界契約**：有服務交換時依 [介接轉寫規則](references/api/writing-rules.md) 投影已確認契約；未承接責任保留移交與缺口。
5. **形成視覺成果**：依 [視覺契約](references/ui/writing-rules.md) 展示已確認行為；有樣式時依 [樣式契約](references/ui/style-spec.md) 同步交付並核對。
6. **驗證與續作**：依驗收規則記錄實際結果和交付判定；補新證據後回查映射、更新計劃並執行受影響的驗證。

## Output Format

依工作方法選用範本，**分別維護**系統行為規格、視覺成果、適用的跨邊界契約、翻新計劃與執行追蹤。以**穩定識別碼和有效連結**連接成果；**缺口標記放在對應契約位置**，處理進度與決策留在計劃及追蹤。

## Evaluation Criteria

- [ ] **證據與覆蓋（R1、R2、R5）**：已界定的行為、分支、互動與副作用有證據及驗證去向。
- [ ] **依賴與決策（R3、R4、R6、R7）**：任務依賴與影響可追蹤；重用契約適用，未轉換資源有明確決策或待決狀態。
- [ ] **局部缺口（R6、R7）**：延後依賴的缺口在實際受影響位置可見，且可連到後續處理。
- [ ] **樣式與客製化（R8）**：元件樣式契約與視覺成果實際使用的樣式有映射與驗證；客製範本版本可追溯。
- [ ] **交付一致性（R8、R9）**：文字與視覺成果一致；必要缺口未解或驗證不足時如實標為部分交付。
