# API-spec 轉寫規則

## 產物定位

[api-spec.md 範本](../assets/integration/api-spec.md) 產生 `artifacts/integration/<scope-id>/api-spec.md`。它是根 JSP 所需 API 的消費投影，不是另建一套後端權威，也不是後端施工藍圖。檔案可包含多個 `API-*` 操作區塊，但只納入本輪實際使用的邊界。

前端 `specification.md` 保持技術中立，以 `BOUND-*` 描述交接語意；API 文件獨立保留後端已定義的協定、method、path、wire schema、header 與結果碼。翻新進度、來源摘錄、差異裁決及待辦細節留在 tracking。

## 轉寫程序

1. 讀 [權威分工](authority.md)，取得指定後端基準及相關共通契約，記錄版本、發布／設計／stub 性質與來源 E。未取得時僅建立具體缺口索引。
2. 從前端 FLOW／BOUND 列出初始化、使用者事件、外部回應等所需能力；先核對是否有對應操作，再轉寫其契約。名稱相近或都叫「查詢」不代表同一操作。
3. 依後端實際識別（operationId，或已確認的 method + path + 契約版本）建立 `API-*`。多個 FLOW 可引用同一 API，一個 FLOW 也可用多個 API；兩者均需有來源證據及順序，不按按鈕或 JSP 函式一對一生成端點。
4. 將操作與共同 envelope、序列化名稱、例外定義一起轉寫，逐筆列 E。只取得局部契約時逐欄標示未知；不能把資料庫型別直接當 wire 型別。
5. 建立雙向映射：前端 DATA／UI／系統情境 → request；response／結果 → DATA／TR／ST／MSG。每個轉換規則需引用前端與後端證據；不存在合法來源或消費位置時說明理由或列 TODO。
6. 核對 JSP 內的後端邏輯是否已被上述 API 承接。未承接的使用 [耦合拆解方法](coupled-source.md) 形成 HANDOFF，不增加未確認 API。
7. 完成契約比對與映射檢查，將案例定義留在規格／API 文件，實際結果留在 tracking。

跨文件引用驗收案例時，逐項核對其前置資料、事件及預期是否實際涵蓋所稱檢查。前端操作案例不自動涵蓋 API 的缺省／空值／型別等 wire 邊界；需要時在介接文件另外定義有獨立 ID 的契約檢查案例並連到定義。不得用存在但內容不同的 AC-ID 代替未定義的案例，也不得把案例定義寫成執行通過。

## 必須逐項保留的事實

- **識別與傳輸**：原 operationId、method、path、參數位置、媒體型別、header、認證／情境來源、上傳／下載及相容路徑。未知不給預設。後端使用何種 method 就保留何種 method，不因通用設計建議而更改。
- **輸入**：精確名稱與大小寫、巢狀路徑、型別、必填條件、缺省／null／空字串／空集合差異、格式、單位、集合順序及來源。前端檢核與後端檢核各自引用，不把其中一個提升為另一個的規則。
- **輸出**：完整已知 envelope 和 payload、缺省與空值、動態集合形狀、已知欄位、代碼、旗標及格式。後端只定義 object／any 時保持動態未知；前端讀到的子欄位記為需求差距，不能補進後端 schema。
- **結果**：HTTP 狀態、業務結果碼、成功／拒絕／錯誤／空值的明確條件與前端反應。HTTP 成功不一定是業務成功；由選定後端契約決定結果判定，不預填 200、0 或 success。
- **性質**：重送、冪等、逾時、取消、分頁、排序、交易邊界與資料副作用只在有依據時描述；未知時不補常見預設。前端的取消展示不等於後端已回滾。
- **來源層級**：正式、設計中與 stub 的能力及環境分開；合成資料不能證明正式 schema 或業務結果。

只轉寫本輪消費的操作；對這些操作，所有已知的必要 header、輸入、envelope、結果分支和相依 schema 不得因畫面只用部分欄位而漏列。未被 UI 使用的已知輸出可以標「未消費」並附範圍理由。

## 缺口與衝突

| 狀況 | 處理 |
| --- | --- |
| 前端需要的初始化資料或行為沒有後端操作 | HANDOFF + TODO，API 缺口索引留 BOUND 與已知需求；不發明 endpoint |
| API 所需欄位在前端無合法來源 | TODO，保留兩端定義；不以 hidden／session 的舊值隨意湊參數 |
| 前端讀取後端未定義的動態欄位 | 記錄 frontend 所需 DATA／UI 與後端缺口；不能改後端 schema 為已確認 |
| legacy 名稱與目標 wire 名稱不同 | 以 API wire 名稱為準，legacy 映射留 tracking；有證據的前端轉換留映射表 |
| 後端文件間／文件與觀察有衝突 | TODO，鎖定尚可確認的部分；沒有基準裁決時不宣告可介接 |
| 後端能力會改變原可見結果／操作順序 | 保留前端原契約和目標差距；未確認的改良不得混入 prototype |

每個 API 文件區塊標明其來源性質與未解契約。已轉寫文件不代表端點已實作、已部署或已通過介接。

## 機器可讀契約

若後端已提供 OpenAPI YAML／JSON，直接引用指定版本與相關操作／schema。需要本輪消費子集時須保留所有必要 `$ref` 及共通定義，使用適用 parser 檢查引用可解析；其權威仍是後端原件。

只有 Markdown 或方法規格時，不主動生成看似正式的 OpenAPI 空殼。需要另轉機器可讀版本時僅轉換已證實內容，沿用後端已指定版本，不新增 server、security scheme、端點、預設狀態或 schema。不足以表達的必要部分以 TODO 留在 Markdown，交付判定為部分，不能拿空 paths 通過 parser 當契約完整。
