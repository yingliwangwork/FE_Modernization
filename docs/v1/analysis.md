# 第一輪差異分析（v1 SoT vs 原始碼）

分析日期：2026-09-15
分析對象：`docs/v1/sot/` 三份 SoT vs `docs/v1/samples.md` 指定的三個 JSP

## 摘要

v1 SoT 在「**這個畫面是做什麼的**」這一層是準確的——功能敘述、區塊劃分、
欄位清單、主要操作流程都對得上原始碼，可讀性也足夠。

但對照驗收條件，v1 **無法通過第 3 條（JSP ↔ IR 互轉無損）與第 5 條（未知須標註）**：

- 共找出 **33 項實質遺漏**，其中 10 項是「照著 SoT 重寫會產生不同行為」的等級。
- SoT 通篇沒有任何「未知」標記，但實際上至少 12 處資訊在本輪條件下不可知，
  v1 把其中多數寫成了確定的敘述（違反驗收條件第 5 條，屬**擅自填補**）。
- 現況的缺陷、死碼、命名不一致完全沒有被記錄。這些正是再工程時最容易
  「默默修好」或「默默照抄」的地方，兩者都會讓新舊系統行為不一致。

---

## 缺口分類

### GAP-1 — 執行階段與求值時機未區分（4 項）

JSP 有兩個執行階段：伺服器產生 HTML 時求值的 `${...}` / `<%= %>`，
以及瀏覽器載入後執行的 JavaScript。v1 SoT 把兩者混為一談。

| # | 位置 | 遺漏內容 |
|---|---|---|
| 1 | `DSC80106.jsp:79` | `'LOAN_ID':'${LOAN_ID}'` 是**伺服器把值寫成 JS 字串字面量**，前端無法改變。SoT §3 寫「畫面在伺服器渲染時會取得」，未點出這是編譯期常數。落地時要選 props 還是 route query，是個決策點，SoT 沒標。 |
| 19 | `AFY10100.jsp:1797-1851` | 列表每一列用 50+ 個 hidden input 承載資料，`id="欄位名${status.index}"`。**列表資料的唯一真實來源是 DOM**，不是任何 JS 物件。這是整個畫面的核心資料流架構，SoT §5.4 只寫「複製到對應欄位」。 |
| 26 | `AFY10100.jsp:450, 1920` | `${isReturn}` 控制核取方塊是否存在、`${isAllow}` 控制 F8 按鈕是否存在——是**伺服器端條件渲染**（元素根本不輸出），不是前端顯示/隱藏。 |
| 12 | `DSC32200.jsp:105,109,57-58` | 日期在「顯示用民國年」與「送出用西元年」之間轉換（`Date.toInputROC` / `toY2K` / `toROC`）。SoT §3.3 只寫「民國年格式」，沒寫**送給後端的是西元年**。 |

### GAP-3 — 演算法與狀態模型遺失（5 項）

| # | 位置 | 遺漏內容 |
|---|---|---|
| 2 | `DSC80106.jsp:85-88` | `$$('#table1 div').each(ele => ele.update(rtnMap[ele.id] \|\| ''))`——**DOM id 即資料契約**，新增一個 div 就等於新增一個欄位，且值以 innerHTML 寫入。SoT 寫成了一般的「填值」。 |
| 9 | `DSC32200.jsp:240,263,269` | 刪除後序號重編的**基準點是 `newSerNO`（後端最後回傳的序號），不是 1**。SoT §5.3 只寫「重新連續編號」，據此重寫會編出錯的號。 |
| 10 | `DSC32200.jsp:130` | `Temp_AMT = Temp_AMT - dataObj.TRANS_AMT + parseInt(new_value)`——**增量維護的累加器**，不是重新加總。SoT §5.5 寫「重算合計金額」。 |
| 17 | `DSC32200.jsp:35-40` | 模組級狀態 `count` / `newSerNO` / `Temp_AMT` / `grid` / `records` 的生命週期沒有被描述，SoT 沒有狀態模型章節。 |
| 28 | `AFY10100.jsp:1723,1787` | 排序呼叫 `sortTable1(col, rtnTable, 'rtnID', ...)`，而 `<tr id="rtnID">` 在 `c:forEach` 中**每列都用同一個 id**。排序機制依賴這個重複 id。 |

依樣本層級：

| 樣本 | 遺漏項數 | 備註 |
|---|---|---|
| `DSC80106`（低） | 8 | 連最簡單的頁面都遺失了核心資料對映機制與錯誤路徑 |
| `DSC32200`（中） | 10 | 三個演算法（序號重編、合計維護、日期轉換）全部描述不足 |
| `AFY10100`（高） | 15 | 核心資料流架構（hidden input 陣列）未被識別 |

**遺漏密度與複雜度正相關，但低複雜度樣本的遺漏比例同樣不可接受**
——代表問題出在缺乏撰寫規則，不是出在檔案太大。

## 方法論待改進項

1. **生成與分析未隔離**：本輪由同一個上下文生成 SoT 並自我審查，
   偵測遺漏的能力弱於獨立審查。實際遺漏數很可能高於 33。
   → 第 2 輪起，生成與分析必須在不同的沙盒上下文執行。
2. **缺乏可機械檢查的驗收清單**：本輪的比對靠人工逐行閱讀，不可重複、不可稽核。
   → v2 需附一份 checklist，讓每一項遺漏都對應到一條可勾選的規則。
3. **外部 JS 未納入分析範圍**：`PageUI.js`、`TableUI.js`、`CSRUtil.js`、
   `validation.js` 的行為直接決定畫面語意，卻不在本輪可讀範圍內。
   → 需決定：是把共用 JS 各自寫成一份共用層 SoT（`jsp-to-vue` 分支已有雛形），
   還是允許 SoT 對其標註未知。**建議前者**。
4. **沒有反向驗證**：驗收條件第 3 條要求「互轉無損」，但本輪沒有做
   「由 SoT 反推 JSP，再與原檔比對」的驗證。
   → v3 應引入反向重建測試，作為無損的客觀判準。

## 對 v2 的要求

依上述缺口，v2 模板需新增下列強制章節：

| 新增章節 | 對應缺口 |
|---|---|
| 渲染契約（伺服器端求值點清單） | GAP-1 |
| 服務契約（endpoint / 請求 / 回應 / 未知標註） | GAP-2 |
| 狀態模型（狀態變數、生命週期、轉換圖） | GAP-3 |
| 演算法規格（以虛擬碼描述，含邊界條件） | GAP-3 |
| 未知清單（`[UNKNOWN]` 明確列舉） | GAP-4 |
| 常數與代碼表 | GAP-5 |
| 現況缺陷登記（`[DEFECT]` / `[DEAD-CODE]`） | GAP-6 |
| 版面規格（結構、語意 class、欄寬、跨欄） | GAP-7 |
| 變更軌跡 | GAP-8 |

撰寫規則見 `docs/v2/rules.md`，模板見 `docs/v2/template.md`。
