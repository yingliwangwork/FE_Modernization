# 第一輪迭代記錄（v1）

執行日期：2026-09-15

## 本輪目的

依研究流程第 1 點，以**最少提示詞**產出初步 SoT，建立可比較的基線，
並據以找出「沒有規則約束時，模型會遺漏什麼」。

## 決策記錄

| # | 決策 | 理由 |
|---|---|---|
| D1 | 中間產物單位＝單一 JSP 檔案 | 使用者指定。單檔粒度讓 SoT 與原始碼可一對一比對，是「互轉無損」的前提。 |
| D2 | 固定三個基準樣本，往後各輪不更換 | 若每輪換樣本，SoT 品質的變化無法歸因於模板/規則的改進。 |
| D3 | 以靜態指標計分後分層隨機抽樣 | 避免人工挑選偏好「好寫的檔案」。抽樣可重現（固定亂數種子）。 |
| D4 | 低/中/高三層各取一件 | 驗證規則在不同複雜度下都成立；低複雜度樣本可暴露「規則本身的缺陷」而非「檔案太大」。 |
| D5 | 本輪不提供模板與規則 | 研究流程第 1 點的要求。刻意讓基線暴露自然遺漏。 |
| D6 | 外部共用 JS 不納入本輪可讀範圍 | 保持「最少提示詞」條件單純。但已確認這是主要的未知來源，列入 v2 待解。 |
| D7 | 原始碼不進版控（`.gitignore` 排除 `**/*.jsp`） | 沿用既有設定。SoT 中以路徑＋行號引用，不整段複製原始碼。 |

## 結論

v1 SoT 在功能敘述層面準確，但**未通過驗收條件第 3 條（互轉無損）與第 5 條（未知須標註）**。

三個關鍵發現：

1. **遺漏集中在「執行階段」與「演算法細節」**，不是集中在功能描述。
   模型自然會寫「這個畫面做什麼」，但不會自發區分伺服器渲染與前端執行，
   也不會把重新編號、累加維護這類邏輯寫到可重寫的精度。
2. **未標註未知是系統性問題**，不是偶發。v1 通篇沒有一個未知標記，
   但實際上至少 12 處資訊在本輪條件下不可知。模型傾向用合理的敘述填補空白。
3. **遺漏比例與複雜度無關**。最簡單的 240 行檔案同樣遺失了核心資料對映機制
   與錯誤路徑，代表問題出在缺乏規則，不是出在檔案規模。
