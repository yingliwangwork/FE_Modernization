# SoT 撰寫規則 v2

本規則與 `docs/v2/template.md` 搭配使用。
每一條規則都源自 `docs/v1/analysis.md` 的具體遺漏，章節標題括號內為對應的缺口編號（GAP-n）。

---

## A. 根本原則

**A1. 保留功能與結構，不保留實作技術。**
「Prototype.js 的 `Event.observe`」是實作技術 → 寫成「載入時執行」。
「刪除後序號以後端回傳值為基準重編」是功能 → 必須逐步寫清楚。

**A2. 判準：一位沒看過原始碼的工程師，能否只憑 SoT 寫出行為一致的畫面？**
凡是做不到的地方，就是 SoT 的缺口。

**A3. 不知道就標 `[UNKNOWN]`，不得推測後以肯定句陳述。**（GAP-4）
若必須推論，標 `[ASSUMPTION]` 並寫出推論依據。
「特定條件下顯示」這種模糊說法**等同未標註**，禁止使用。

**A4. 現況即事實。**（GAP-6）
缺陷、死碼、命名不一致、未處理的錯誤路徑，一律照實記錄並標記。
SoT 的工作是描述系統現在是什麼樣子，不是描述它應該是什麼樣子。

---

## B. 執行階段（GAP-1）

**B1.** 伺服器端求值（`${...}`、`<%= %>`、`<% %>`）與瀏覽器端執行，
必須在 SoT 中明確分開，不得混寫為「取得某值」。

**B2.** 每一個伺服器端求值點都要進 §3 渲染契約表，
說明求值結果的**落點**（JS 字串字面量 / HTML 屬性 / 文字節點）
與**前端可否變更**。

**B3.** 伺服器端條件渲染（元素是否輸出）與前端顯示/隱藏是兩件事，
必須分別記錄在 §3.1 與 §7.2。

**B4.** 凡是「顯示格式」與「送出格式」不同的欄位（民國年/西元年、
千分位/純數字），兩種格式都要寫，並註明轉換發生在哪個時點。

---

## C. 服務契約（GAP-2）

**C1.** 每個後端呼叫獨立一節，位址、方式、觸發、請求、回應、失敗處理六項齊全。

**C2.** 請求參數要逐一列出，並標明**每個參數的來源**
（伺服器渲染時嵌入 / 使用者輸入 / 前次回應帶回）。

**C3.** 出現在請求中但畫面上沒有對應元素的參數（「只進不出」），
要在 §5 欄位表外另行點명。

**C4.** 失敗處理若原始碼沒有寫，就寫「無」並標 `[DEFECT]`。
不得省略此列，也不得補上一個原始碼沒有的錯誤處理。

**C5.** 後端提供的代碼對照表一律列進 §11.2，名稱與用途都要寫。

---

## D. 演算法與狀態（GAP-3）

**D1.** 凡是包含迴圈、條件分支、累加、重新編號、格式轉換的邏輯，
一律進 §8 並以虛擬碼描述。只寫「重新編號」「重算合計」不算數。

**D2.** 虛擬碼必須標明**基準點與初值來源**
（例：序號重編的起點是後端回傳的 `newSerNO`，不是 1）。

**D3.** 累加器要寫清楚是**增量維護**還是**每次重算**，兩者行為不同。

**D4.** 每個演算法都要寫邊界條件：空值、零筆、全選、型別轉換失敗。

**D5.** 模組級狀態變數一律進 §7.1，含初值、意義、由誰改變、生命週期。

**D6.** 元素的啟用/停用、顯示/隱藏視為狀態，進 §7.2 轉換表。

---

## E. 未知（GAP-4）

**E1.** §14 未知清單不得為空。沒有未知項時，須寫明查證範圍。

**E2.** 下列情形一律列為未知：
- 呼叫了本檔未定義、且其原始碼不在本輪可讀範圍內的函式
- 由呼叫端決定的回呼契約
- 伺服器提供但格式未說明的資料
- 依賴外部元件的行為（表格元件、驗證元件、彈窗元件）

**E3.** 每個未知項要寫「影響範圍」與「建議澄清方式」，
讓後續輪次能據以決定是否補樣分析。

**E4.** 外部共用腳本（`PageUI.js`、`TableUI.js`、`CSRUtil.js`、`validation.js`…）
一律列入 §13 相依清單，並標明本 SoT 是否已知其行為。

---

## F. 常數（GAP-5）

**F1.** 所有硬編碼字面值（帳號、代碼、頁大小、預設值）進 §11.1，
含出現位置與意義。

**F2.** 條件分支的比較值要寫**代碼本身**，不能只寫中文語意。
「暫收原因為入案款」不夠，要寫「`BALC_REASON == 15`（入案款）」。

**F3.** 畫面上的靜態代碼說明文字（保單狀況、繳別、險種…）**完整抄錄**，
不得摘要或省略。那是業務規則的一部分。

---

## G. 缺陷（GAP-6）

**G1.** §15 缺陷登記不得為空。沒有時須寫明「經查後無」。

**G2.** 下列一律登記：
- 重複的 DOM 識別碼
- 未處理的錯誤路徑
- 顯示欄位與送出欄位取值不一致
- 未做編碼的參數串接
- 無終止條件或高頻的計時器
- HTML 結構錯誤（標籤重複、未閉合、巢狀錯誤）
- 語法瑕疵（缺分號、多餘結束標籤）
- 空元素、永不執行的分支

**G3.** 每一項要寫「再工程處置建議」：保留現況 / 修正（需業務確認）。
SoT 不自行決定修不修。

**G4.** 用字不一致（同一概念在不同區塊寫法不同）視為缺陷，要登記。

---

## H. 版面（GAP-7）

**H1.** 樣式名稱要對映到語意（標籤欄 / 值欄 / 表頭 / 交替列），
不是照抄 class 名稱。

**H2.** 欄寬、`colspan`、`rowspan`、對齊方式要記錄——
它們承載「哪些欄位是一組」的資訊。

**H3.** 逐欄位套用的樣式（如造字字型）要標明套用到**哪些欄位**，
不得寫成全域設定。

**H4.** 「一個欄位由顯示元素＋隱藏元素成對組成」這類模式要明寫，
並說明哪一個負責顯示、哪一個負責送出。

---

## I. 軌跡（GAP-8）

**I1.** 檔頭註解（程式名、作者、完成日、修改記錄）完整搬進 §0 與 §16。

**I2.** 程式碼中帶單號或日期的變更註記，連同其對應的程式位置進 §16。
那是業務決策的唯一書面來源。

**I3.** 版型痕跡、產生器註解等來源歷史資訊，記在 §16 或 §0 備註。

---

## J. 落地決策點

**J1.** SoT 不替目標技術做決定。凡是有多種合理落地方式的地方，
列進 §17 決策點，寫明現況、選項、影響。

**J2.** 典型決策點：
- 伺服器渲染時嵌入的值 → 改為 props、路由參數、還是初始化 API？
- 以 DOM 為真實資料來源的機制 → 改為前端狀態模型後，哪些行為會變？
- 整頁表單送出 → 改為非同步請求後，訊息顯示與頁面狀態如何處理？
- 現況缺陷 → 保留或修正？

---

## K. 產出檢查清單

送出 SoT 前逐項確認：

- [ ] §3 渲染契約：原始碼中每一個 `${...}` / `<%= %>` 都有對應列
- [ ] §3.1 條件渲染：每個條件輸出的元素都有列，判定規則已知或已標未知
- [ ] §5 欄位規格：每個輸入/顯示元素都有列，且「送出」欄已填
- [ ] §5.1 顯示與送出不一致者已逐項列出
- [ ] §6 每個後端呼叫都有「失敗處理」列
- [ ] §7.1 每個模組級變數都有列
- [ ] §8 每個含分支或迴圈的邏輯都有虛擬碼與邊界條件
- [ ] §9 每條驗證規則都有觸發時機
- [ ] §10 每個熱鍵都註明目標元素的存在條件
- [ ] §11.1 每個硬編碼字面值都有列
- [ ] §11.2 畫面上的代碼說明文字已完整抄錄
- [ ] §13 每個外部腳本都有列，且標明行為是否已知
- [ ] §14 未知清單非空（或已寫明查證範圍）
- [ ] §15 缺陷登記非空（或已寫明經查後無）
- [ ] §16 檔頭註解與變更註記已搬入
- [ ] §17 決策點已列出
- [ ] 全文無「特定條件」「某些情況」「相關處理」這類模糊措辭
- [ ] 全文無任何目標框架名稱（Vue / React / Angular）
